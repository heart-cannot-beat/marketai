# Three Meta evidence modes with Platform Workspace isolation

Every Meta evidence row carries an immutable (workspace_id, meta_mode) provenance pair enforced by RLS USING/WITH CHECK on both columns and composite foreign keys that include (workspace_id, meta_mode, …) to prevent cross-mode references at the schema level. The three modes are: customer_sandbox — no network calls, curated scenario data via a durable database-backed FakeMetaAdapter, persisted through full domain paths and eligible for Scale verdicts and Experiment decisions; controlled_mock — no network calls, fault-injection scenarios via the same FakeMetaAdapter, persisted through full domain paths but explicitly excluded from decision eligibility, serving only to exercise adapter error handling and partial-failure recovery; and internal_validation — real HTTP read-only calls to the Meta API, restricted to a Platform Workspace (is_platform_workspace flag, platform-operator membership required, enforced at the domain service level, not only the BFF) and authenticated via a separate platform-operator JWT with its own issuer, audience, and JWKS endpoint. Mode is immutable provenance, not a maturity ladder: evidence cannot be "promoted" by changing its label but must be re-observed and evaluated in the destination mode. Cross-mode administration and reconciliation use a separate, explicitly privileged and audited path. Workers set both workspace_id and meta_mode with transaction-scoped SET LOCAL and fail closed when either is missing; application roles cannot bypass RLS, and FORCE ROW LEVEL SECURITY applies where needed. We rejected a two-mode model (collapsing sandbox and mock loses the distinction between decision-eligible curated evidence and test-only fault-injection evidence), customer-workspace real reads (before the full BYOK token lifecycle in #9, this would create credential isolation gaps and mix real evidence with sandbox evidence in the same workspace), mode promotion (changing an evidence row's mode violates the append-only immutable-provenance invariant and could contaminate decision pipelines), and RLS-only isolation without composite foreign keys (RLS controls visibility but cannot prevent cross-mode references in joins and foreign keys; schema-level relational constraints provide defense in depth).
